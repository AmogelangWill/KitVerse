Getting the backend running on your machine

stuff you need installed first

.NET 10 SDK — grab it from https://dotnet.microsoft.com/en-us/download/dotnet/10.0 (the SDK, not just the runtime). Once it's in, check it worked:

run thw following in your command line
```
dotnet --version
```
Should say something like `10.0.302`.

EF Core CLI tool — this is separate from the SDK, one-time install per machine:
```
dotnet tool install --global dotnet-ef
```

Getting the project

```
git clone https://github.com/AmogelangWill/KitVerse.git
cd KitVerse/backend
dotnet restore
```

That last command pulls in all the NuGet packages the project needs (EF Core, Npgsql, etc).

Connecting to the database

Here's the part that's not automatic: the database connection string isn't in the repo on purpose, since it's basically a password and shouldn't ever end up on GitHub. So you need to set it up yourself, once:

run this to connect to the SUPABASE 
```
dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:SupabaseConnection" "Host=aws-1-eu-west-1.pooler.supabase.com;Port=5432;Database=postgres;Username=postgres.sekbsdzqbykvocywwxsq;Password=LuminarProtocol@Devs;SSL Mode=Require;Trust Server Certificate=true"

```
we used a session pooler instead because it was the faster one in terms of connecting 

Run it

```
dotnet build
dotnet run
```

If that builds clean and starts up, you're good to go.

A couple of rules worth sticking to

Don't touch the database schema directly in Supabase. No manually running `CREATE TABLE` or `ALTER TABLE` in the SQL editor — if we start doing that, EF Core's migrations and the actual database drift out of sync and things get confusing fast. All schema changes go through code... infact if there are any suggestions with the scemas then you would notify me :

steps to follow should you wish to add a schema

1. Add/edit the entity class in `Models/`
2. Update `Data/KitverseDbContext.cs` — add the `DbSet` and the mapping in `OnModelCreating`
3. `dotnet ef migrations add SomeDescriptiveName`
4. `dotnet ef database update`
5. Commit the new migration files along with everything else — that's what lets it apply automatically for everyone else next time they pull

Never commit the real connection string. It only ever lives in `dotnet user-secrets` on your own machine, never in `appsettings.json`, never pushed anywhere.

If something's not working

- Getting connection timeouts talking to Supabase → you're probably on the Transaction Pooler string instead of Session Pooler, swap it.
- `"UserSecretsId not found"` error → you skipped `dotnet user-secrets init`, run that first.
- Random build errors after pulling → run `dotnet restore` again, probably a new package got added.

 every command must be back to back

```
git clone https://github.com/AmogelangWill/KitVerse.git
cd KitVerse/backend

dotnet restore

dotnet user-secrets init
dotnet user-secrets set "ConnectionStrings:DATABASE_URL" "Host=aws-1-eu-west-1.pooler.supabase.com;Port=5432;Database=postgres;Username=postgres.sekbsdzqbykvocywwxsq;Password=LuminarProtocol@Devs;SSL Mode=Require;Trust Server Certificate=true"

dotnet build
dotnet run
```
